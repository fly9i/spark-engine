# 在三台 DGX Spark 上运行 DeepSeek-V4.1-Flash（TP3）

本文是用 spark-engine 在三台 DGX Spark 上服务 **DeepSeek-V4.1-Flash-1017**（`deepseek-ai/DeepSeek-V4.1-Flash-1017`，MIT）
的完整方法。这是本项目自己运行的部署，所用二进制与服务 GLM-5.3-Flash 和 Qwen3.8-Flash-Next 的相同（`start.sh ds41`）。
通用部分（主机设置、安装、Python 环境）请先阅读 [deploy.zh-CN.md](deploy.zh-CN.md)。

## 1. 各部分在哪里运行

| | |
| --- | --- |
| 检查点 | 官方 HF safetensors，原样使用：路由专家为 MXFP4（E2M1 + 每 32 一个 E8M0），其他权重为带 32×32 E8M0 块 scale 的 FP8 E4M3 或 BF16；48 个文件，约 510 GB |
| 切分（TP3） | 注意力按头组 3/3/2 切分（`wo_a` 按组块对角），路由专家和共享专家按中间维度切分（每个节点 768，完全均衡），词表按 128 行块切分；mHC、norm、router、compressor、indexer 和 Engram 投影在各节点复制 |
| 每个节点 | 常驻约 96 GB 权重，KV 池约 3.3 GiB（1.1 M token），其余留给 graph、workspace 和操作系统 |
| Engram | 两张 n-gram 表（203 GB，位于检查点内）留在各节点的 NVMe 上按需读取（每 token 约 12.7 KB，O_DIRECT，提前一个 prefill 块预取）；不载入内存、不切分、无跨节点流量 |
| Prefill | CED：编码器（第 0–19 层）处理每个 token，解码器（第 20–39 层）只处理最后一个窗口（decoder SWA bounded replay） |
| 解码 | DSpark 投机解码（检查点自带的 3 个草稿级，每步 5 个草稿位置；每个序列的草稿数由代价模型选择）；超过 4 个序列时为普通批量解码 |
| 传输 | 引擎自带的 N 路 RDMA all-reduce / reduce-scatter / all-gather（FP32 按固定 rank 顺序求和）；NCCL 只用于引导 |
| 服务 | OpenAI 兼容 API，4 个并发序列，1M token 上下文，NVMe 前缀缓存，图片输入（rank 0 运行视觉编码器） |

对照官方参考实现（用纯 torch、逐层流式运行检查点自带的 `inference/model.py`）实测的精度：prefill KL 0.0236 / top-1 0.957，
噪声地板（两个精确实现相互比较）为 0.0224 / 0.955。

## 2. 硬件与网络

| | 每个节点 |
| --- | --- |
| 机器 | 3× DGX Spark（GB10，128 GB 统一内存） |
| 磁盘 | 约 510 GB 检查点 + 约 97 GB 分片 + 最多 100 GB 前缀缓存（`DS41_PCACHE_GB`）；需要快速 NVMe（prefill 期间从中读取 Engram 行） |
| 网络 | ConnectX-7 QSFP 端口全互连：每对节点一根线缆，外加一个三台互相可达的局域网 |

每个 QSFP 端口表现为两个 RDMA 设备（两个 PCIe function）。给每个 function 配一个独立的点对点 /30，这样每对节点有两条链路。
本项目使用的布局（节点 A 运行 rank 0 和前端）：

| 链路 | 接口（两端） | 节点 A | 节点 B | 节点 C |
| --- | --- | --- | --- | --- |
| A–B，端口 0 | `enp1s0f0np0` | 10.0.1.2/30 | 10.0.1.1/30 | |
| A–B，端口 0 | `enP2p1s0f0np0` | 10.0.2.2/30 | 10.0.2.1/30 | |
| A–C，A 上的端口 1 | `enp1s0f1np1` | 10.0.3.1/30 | | 10.0.3.2/30 |
| A–C，A 上的端口 1 | `enP2p1s0f1np1` | 10.0.4.1/30 | | 10.0.4.2/30 |
| B–C | B 和 C 的剩余端口，两个 function | | 10.0.5.1/30、10.0.6.1/30 | 10.0.5.2/30、10.0.6.2/30 |

无需配置设备名或 GID：每个 rank 发布自己的 RoCE 设备及其 IPv4 地址和前缀，处于同一子网的任意两个设备即构成一条链路（一根
线缆的两个 function 都会用上）。启动日志会显示配对结果，例如 `rank0<->rank1: roceP2p1s0f0(gid 3) rocep1s0f0(gid 3)`；
`no RoCE subnet shared with rankN` 表示地址没有配上对。`GLM53_RDMA_ARN_GID` 覆盖 GID 索引；`GLM53_RDMA_ARN_CPUS`
（默认 `19,18,17`）绑定代理线程所用的 CPU。

每个工作节点经自己的直连链路访问 rank 0，因此各 rank 看到的 rank 0 地址不同：按上面的布局，
`SPARK_MASTER_ADDRS="10.0.1.2 10.0.1.2 10.0.3.1"`。NCCL 引导使用 `SPARK_TP3_IFNAME`，即局域网接口。

**三个**节点上的主机设置：关闭 swap，使用 [deploy.zh-CN.md](deploy.zh-CN.md) §1 的 sysctl 设置
（`vm.compaction_proactiveness = 0`、`vm.watermark_boost_factor = 0`），不运行桌面会话或其他占用 GPU / CPU 的重负载。
rank 0 上内存紧张（就绪时留给操作系统的约 5–6 GiB）；内存耗尽的节点可能卡死。

## 3. 安装

在每个节点上，按 [deploy.zh-CN.md](deploy.zh-CN.md) §3：在相同路径下安装发布包（或源码构建）和 Python 环境，并为运行服务的
用户配置从节点 A 到 B、C 的免密 ssh。如果三个节点的引擎二进制不一致，启动脚本会拒绝启动。

Python 环境还需要 `sympy`（用于下面的 Engram 哈希导出）：

```bash
/opt/spark-engine/.venv/bin/pip install sympy
```

## 4. 权重

在**每个**节点上（每个 rank 都内存映射检查点，并从自己的副本读取 Engram 表）：

```bash
PATH=/opt/spark-engine/.venv/bin:$PATH /opt/spark-engine/scripts/download-models.sh ds41 /models
```

该脚本固定版本 `1bae0e1088993b9b82de08f59de5be5a34e42170`。三个节点使用相同的绝对路径；也可以下载一次后用 `rsync` 复制。
如果是复制的，请对照 Hugging Face 文件页面（LFS）上显示的 sha256 校验文件。

### 4.1 分片（每个节点一次，约 5 分钟，约 97 GB）

每个 rank 加载预先切好的分片，而不是在启动时切分 510 GB。在节点 A 上运行 rank 0，B 上 rank 1，C 上 rank 2（下面的 `r`），
此时不要有其他程序使用 GPU：

```bash
source /opt/spark-engine/scripts/env.sh
ckpt=/models/DeepSeek-V4.1-Flash-1017; out=/models/ds41-tp3-1017
bin/spark-engine ds41-shard     $ckpt $out/rank$r $r 3
bin/spark-engine ds41-shard-mtp $ckpt $out/rank$r $r 3
bin/spark-engine ds41-shard-pack $out/rank$r
```

分片会记录其检查点的绝对路径（Engram 表和视觉编码器从那里读取）：如果移动了检查点，需要重新分片。

### 4.2 Engram 哈希常量（一次，复制到每个节点）

引擎从一个 JSON 文件读取 n-gram 哈希常量（分词器映射、素数、偏移、乘数），该文件由检查点自带的 `inference/engram.py`
生成，因此从构造上就与官方实现一致：

```bash
.venv/bin/python -I reference/ds41/export_engram.py --ckpt /models/DeepSeek-V4.1-Flash-1017 --out /models/ds41-engram_hash.json
```

它在 CPU 上运行，不到一分钟（`reference/ds41/kernel.py` 替代 `model.py` 所导入的检查点 tilelang 内核）。把该文件放到三个
节点的相同路径下。最初的 DeepSeek-V4.1-Flash 发布版使用相同的常量。

## 5. 设置

在 `spark.env` 中（每个节点同一份文件；见 [configuration.zh-CN.md](configuration.zh-CN.md)）：

```bash
SPARK_WORKERS="root@10.0.1.1 root@10.0.3.2"       # ranks 1 and 2
SPARK_MASTER_ADDRS="10.0.1.2 10.0.1.2 10.0.3.1"   # rank 0 as seen from rank 0, 1, 2
SPARK_TP3_IFNAME=eth0                             # your LAN interface (ip -br addr)

DS41_CKPT=/models/DeepSeek-V4.1-Flash-1017
DS41_SHARDS=/models/ds41-tp3-1017
DS41_ENGRAM_HASH=/models/ds41-engram_hash.json
DS41_MODEL_NAME=DeepSeek-V4.1-Flash-1017
```

每个 rank 自己读取 `spark.env`，因此写在其中的 `DS41_*` 设置会作用于全部三个 rank（它们必须一致：各 rank 设置不同时前缀
缓存会拒绝启动）。默认值即生产设置：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `DS41_SERVE_STORES` | `4` | 并发序列数（前端以相同的上限启动）。 |
| `DS41_MTP` / `DS41_SPEC` | `1` / `1` | 加载 DSpark 草稿级（每 rank 约 2.7 GiB）/ 使用它们。每个序列的草稿数来自代价模型 `DS41_SPEC_COST`（`24,0.6,5`：基础、每序列、每行，单位 ms）；超过 `DS41_SPEC_MAX_BATCH`（4）个序列时为普通批量解码。 |
| `DS41_PREFILL_CHUNK` | `4096` | prefill 块大小（token）。 |
| `DS41_KV_TOKENS` | `1100000` | KV 池大小，上限为预热后空闲内存最少的 rank 所能容纳的量；池所允许的最长请求会在 ready 行中报告并传给前端（默认值下为 1,048,576）。 |
| `DS41_VISION` | `1` | 图片输入（rank 0 加载 ViT，约 1 GiB）。 |
| `DS41_PCACHE` | `1` | NVMe 前缀缓存：`DS41_PCACHE_DIR`（默认 `$SPARK_HOME/var/ds41-prefix-cache`，各节点本地），每个节点最多 `DS41_PCACHE_GB`（100）GB，LRU，保持磁盘至少 `DS41_PCACHE_FREE_GB`（20）GB 空闲；每 512 token 一个检查点。 |
| `DS41_MEM_MARGIN_GB` / `DS41_MEM_HEADROOM_GB` | `5` / `2` | 确定 KV 池大小时留给操作系统的内存和余量。 |
| `DS41_RELEASE_FILE_CACHE`、`DS41_HOST_TRIM`、`DS41_MALLOC_TUNE` | `1` | 主机内存：预热后释放检查点的文件页、归还 glibc 的空闲页、限制 glibc arena 数（没有这些设置时，负载下主机 RSS 会增长数 GB）。 |
| `DS41_ABLATE_CLAMP` | 空（关闭） | 可选的条件钳制消融；见 [abliteration.zh-CN.md](abliteration.zh-CN.md)。 |
| `DS41_MASTER_PORT` | `29961` | 进程组端口（控制通道使用该值 + 31）。 |
| `DS41_EXTRA_ENV` | — | 对每个 rank 生效的额外 `NAME=value` 设置，例如诊断用的 `DS41_STEP_STATS=1 DS41_PREFILL_STATS=1`。 |

## 6. 启动、使用、停止

```bash
engine-rs/serve/start.sh ds41      # on node A; stops whatever model runs first
engine-rs/serve/start.sh status    # ds41
engine-rs/serve/start.sh stop
```

检查点页已在缓存中时，加载约 20 s，外加约 10 s 预热；从冷磁盘加载更久。日志：`/tmp/spark-ds41-rank<r>.log`（在各节点上）、
`/tmp/spark-ds41-front.log`。每个请求在 rank 0 上记录一行，例如 `request: prompt N tokens, prefix M from store|disk|cold`。

API 与其他模型相同（[deploy.zh-CN.md](deploy.zh-CN.md) §6）。前端（`engine-rs/serve/ds41_server.py`）针对 DeepSeek 的行为：

- **提示词**由检查点自带的 `encoding/encoding.py` 构建（多轮、工具、思考、对话中途的 system 消息），因此格式与官方参考完全一致。
- **采样**：`temperature` 默认 1.0（DeepSeek 的推荐值；可用 `DS41_DEFAULT_TEMPERATURE` 修改）；未提供 `seed` 时每个请求使用
  随机 seed。`top_p`、`top_k` 和各类惩罚参数会被接受，但不生效。`max_tokens` 默认 8192。
- **思考**默认开启。用 `"chat_template_kwargs": {"thinking": false}`（或 `enable_thinking`）或 `"reasoning_effort": "none"`
  关闭。强度等级映射到模型的 1–100 预算：`low` 50、`medium` 62、`high` 75、`xhigh`/`max` 100，也可以直接传整数。
- **工具**：OpenAI `tools` / `tool_calls` / 角色 `tool`；调用从模型的 DSML 块中解析。要让跨轮次的前缀缓存命中，应把每个会话中
  会变化的部分放在工具定义之后，并把之前的 assistant 轮次按收到的原样发回。
- **图片**：`image_url` 部分（每张图片最多 1024 token）；视频会以 HTTP 400 拒绝。

## 8. 故障排查

| 现象 | 原因 / 解决方法 |
| --- | --- |
| `engine binary differs on rank N` | 在三个节点的 `SPARK_BIN` 处安装同一个二进制。 |
| `no RoCE subnet shared with rankN` | 这对节点的点对点地址不在同一子网；检查 `ip -br addr` 和布线。 |
| `rank 0 exited`、进程组错误 | 某个节点上 `SPARK_TP3_IFNAME` 缺失或错误、`DS41_MASTER_PORT` 被占用，或某个工作节点失败：查看节点 B 和 C 上的 `/tmp/spark-ds41-rank1.log` / `rank2.log`。 |
| 启动时内存不足 / KV 池断言失败 | 某个节点上有其他进程占用内存，或上一个模型仍在释放内存：执行 `start.sh stop`，等待后再启动。 |
| 启动时前缀缓存被禁用 | 各 rank 的身份不一致：三个节点上的二进制、检查点路径、哈希文件和 `DS41_*` 设置需相同。 |
| 冷 prefill 慢 | Engram 行来自 NVMe：检查点应放在本地 NVMe 上，而不是网络盘或 USB 盘。 |
