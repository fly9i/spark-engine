# DeepSeek-V4.1-Flash on three DGX Sparks (TP3)

This is the complete recipe for serving **DeepSeek-V4.1-Flash-1017** (`deepseek-ai/DeepSeek-V4.1-Flash-1017`, MIT) with
spark-engine on three DGX Sparks. It is the deployment the project runs itself, with the same binary that serves
GLM-5.3-Flash and Qwen3.8-Flash-Next (`start.sh ds41`). Read [deploy.md](deploy.md) first for the common parts (host
settings, install, the Python environment).

## 1. What runs where

| | |
| --- | --- |
| Checkpoint | official HF safetensors, unchanged: routed experts MXFP4 (E2M1 + E8M0 per 32), other weights FP8 E4M3 with 32×32 E8M0 block scales or BF16; 48 files, ~510 GB |
| Split (TP3) | attention by head groups 3/3/2 (`wo_a` is block-diagonal per group), routed and shared experts by the intermediate dimension (768 per node, exactly balanced), vocabulary in 128-row blocks; mHC, norms, router, compressor, indexer and Engram projections replicated |
| Per node | ~96 GB of weights resident, KV pool ~3.3 GiB (1.1 M tokens), the rest for graphs, workspace and the OS |
| Engram | the two n-gram tables (203 GB, inside the checkpoint) stay on each node's NVMe and are read on demand (~12.7 KB per token, O_DIRECT, prefetched one prefill chunk ahead); not loaded into memory, not split, no cross-node traffic |
| Prefill | CED: the encoder (layers 0–19) runs every token, the decoder (20–39) only the last window (decoder SWA bounded replay) |
| Decoding | DSpark speculative decoding (the checkpoint's 3 draft stages, 5 draft positions per step; the number of drafts per sequence is chosen by a cost model); plain batched decode above 4 sequences |
| Transport | the engine's N-way RDMA all-reduce / reduce-scatter / all-gather (FP32 sums in fixed rank order); NCCL only bootstraps |
| Serving | OpenAI-compatible API, 4 concurrent sequences, 1M-token context, NVMe prefix cache, image input (rank 0 runs the vision encoder) |

Measured accuracy against the official reference implementation (a pure-torch, layer-streamed run of the checkpoint's
own `inference/model.py`): prefill KL 0.0236 / top-1 0.957, against a noise floor (two exact implementations compared
with each other) of 0.0224 / 0.955.

## 2. Hardware and network

| | per node |
| --- | --- |
| Machines | 3× DGX Spark (GB10, 128 GB unified memory) |
| Disk | ~510 GB checkpoint + ~97 GB shard + up to 100 GB prefix cache (`DS41_PCACHE_GB`); a fast NVMe (Engram rows are read from it during prefill) |
| Network | a full mesh of the ConnectX-7 QSFP ports: one cable per pair of nodes, plus a LAN on which all three reach each other |

Each QSFP port appears as two RDMA devices (two PCIe functions). Give each function its own point-to-point /30, so each
pair of nodes has two links. The layout the project uses (node A runs rank 0 and the front end):

| Link | Interface (both ends) | Node A | Node B | Node C |
| --- | --- | --- | --- | --- |
| A–B, port 0 | `enp1s0f0np0` | 10.0.1.2/30 | 10.0.1.1/30 | |
| A–B, port 0 | `enP2p1s0f0np0` | 10.0.2.2/30 | 10.0.2.1/30 | |
| A–C, port 1 on A | `enp1s0f1np1` | 10.0.3.1/30 | | 10.0.3.2/30 |
| A–C, port 1 on A | `enP2p1s0f1np1` | 10.0.4.1/30 | | 10.0.4.2/30 |
| B–C | the remaining port of B and C, both functions | | 10.0.5.1/30, 10.0.6.1/30 | 10.0.5.2/30, 10.0.6.2/30 |

No device names or GIDs need configuring: every rank publishes its RoCE devices with their IPv4 address and prefix,
and any two devices on a shared subnet become a link (both functions of a cable are used). The startup log shows the
pairing, e.g. `rank0<->rank1: roceP2p1s0f0(gid 3) rocep1s0f0(gid 3)`; `no RoCE subnet shared with rankN` means the
addresses do not pair up. `GLM53_RDMA_ARN_GID` overrides the GID index; `GLM53_RDMA_ARN_CPUS` (default `19,18,17`)
pins the proxy threads.

Each worker reaches rank 0 over its own direct link, so the address of rank 0 differs per rank: with the layout above
`SPARK_MASTER_ADDRS="10.0.1.2 10.0.1.2 10.0.3.1"`. NCCL's bootstrap uses `SPARK_TP3_IFNAME`, the LAN interface.

Host settings on **all three** nodes: swap off, the sysctl settings of [deploy.md](deploy.md) §1
(`vm.compaction_proactiveness = 0`, `vm.watermark_boost_factor = 0`), no desktop session or other GPU / CPU-heavy work.
Memory is tight on rank 0 (about 5–6 GiB left for the OS at ready); a node that runs out of memory can hang.

## 3. Install

On every node, as in [deploy.md](deploy.md) §3: the release (or a source build) at the same path, the Python
environment, and passwordless ssh from node A to B and C for the user that runs the server. The launcher refuses to
start if the three engine binaries differ.

The Python environment also needs `sympy` (for the Engram hash export below):

```bash
/opt/spark-engine/.venv/bin/pip install sympy
```

## 4. Weights

On **every** node (each rank memory-maps the checkpoint and reads the Engram tables from its own copy):

```bash
PATH=/opt/spark-engine/.venv/bin:$PATH /opt/spark-engine/scripts/download-models.sh ds41 /models
```

This pins revision `1bae0e1088993b9b82de08f59de5be5a34e42170`. Use the same absolute path on the three nodes; downloading
once and copying with `rsync` works too. Check the files against the sha256 values shown on the Hugging Face file
pages (LFS) if you copy them.

### 4.1 Shards (once per node, ~5 min, ~97 GB)

Each rank loads a pre-split shard instead of slicing 510 GB at start-up. On node A run rank 0, on B rank 1, on C rank 2
(`r` below), with nothing else using the GPU:

```bash
source /opt/spark-engine/scripts/env.sh
ckpt=/models/DeepSeek-V4.1-Flash-1017; out=/models/ds41-tp3-1017
bin/spark-engine ds41-shard     $ckpt $out/rank$r $r 3
bin/spark-engine ds41-shard-mtp $ckpt $out/rank$r $r 3
bin/spark-engine ds41-shard-pack $out/rank$r
```

A shard records the absolute path of its checkpoint (the Engram tables and the vision encoder are read from there):
if you move the checkpoint, shard again.

### 4.2 Engram hash constants (once, copy to every node)

The engine takes the n-gram hashing constants (tokenizer map, primes, offsets, multipliers) from a JSON file produced
by the checkpoint's own `inference/engram.py`, so they match the official implementation by construction:

```bash
.venv/bin/python -I reference/ds41/export_engram.py --ckpt /models/DeepSeek-V4.1-Flash-1017 --out /models/ds41-engram_hash.json
```

It runs on the CPU in under a minute (`reference/ds41/kernel.py` stands in for the checkpoint's tilelang kernels, which
`model.py` imports). Put the file at the same path on all three nodes. The original DeepSeek-V4.1-Flash release has
the same constants.

## 5. Settings

In `spark.env` (same file on every node; see [configuration.md](configuration.md)):

```bash
SPARK_WORKERS="root@10.0.1.1 root@10.0.3.2"       # ranks 1 and 2
SPARK_MASTER_ADDRS="10.0.1.2 10.0.1.2 10.0.3.1"   # rank 0 as seen from rank 0, 1, 2
SPARK_TP3_IFNAME=eth0                             # your LAN interface (ip -br addr)

DS41_CKPT=/models/DeepSeek-V4.1-Flash-1017
DS41_SHARDS=/models/ds41-tp3-1017
DS41_ENGRAM_HASH=/models/ds41-engram_hash.json
DS41_MODEL_NAME=DeepSeek-V4.1-Flash-1017
```

Every rank reads `spark.env` itself, so `DS41_*` settings placed there reach all three ranks (they must be identical:
the prefix cache refuses to start when the ranks' settings differ). The defaults are the production settings:

| Variable | Default | Meaning |
| --- | --- | --- |
| `DS41_SERVE_STORES` | `4` | Concurrent sequences (the front end is started with the same limit). |
| `DS41_MTP` / `DS41_SPEC` | `1` / `1` | Load the DSpark draft stages (~2.7 GiB per rank) / use them. Drafts per sequence come from the cost model `DS41_SPEC_COST` (`24,0.6,5`: base, per sequence, per row, in ms); above `DS41_SPEC_MAX_BATCH` (4) sequences, plain batched decode. The draft's Markov / Gumbel sampling / confidence steps run as one CUDA graph (`DS41_DRAFT_GRAPH=0` goes back to a host round trip per draft; `DS41_DRAFT_GRAPH_CHECK=1` compares both bitwise every round). |
| `DS41_ENGRAM_Q` | `1` | Prefill feeds the Engram projection the act-quantized operands computed straight from the table's FP8 bytes (bitwise the same as dequantizing to BF16 first, which `0` does). |
| `DS41_PREFILL_CHUNK` | `4096` | Prefill chunk (tokens). |
| `DS41_KV_TOKENS` | `1100000` | KV pool size, capped by the smallest rank's free memory after warm-up; the longest request the pool allows is reported in the ready line and given to the front end (1,048,576 at the default). |
| `DS41_VISION` | `1` | Image input (rank 0 loads the ViT, ~1 GiB). |
| `DS41_PCACHE` | `1` | NVMe prefix cache: `DS41_PCACHE_DIR` (default `$SPARK_HOME/var/ds41-prefix-cache`, local to each node), at most `DS41_PCACHE_GB` (100) GB per node with LRU, keeps `DS41_PCACHE_FREE_GB` (20) GB of disk free; checkpoints every 512 tokens. Checkpoints inside a long prefill (the decoder last ran a window or more before them) leave out the 20 decoder window rings (2.5 MiB each), which the restore never reads. |
| `DS41_MEM_MARGIN_GB` / `DS41_MEM_HEADROOM_GB` | `5` / `2` | Memory left to the OS and headroom when sizing the KV pool. |
| `DS41_RELEASE_FILE_CACHE`, `DS41_HOST_TRIM`, `DS41_MALLOC_TUNE` | `1` | Host memory: drop the checkpoint's file pages after warm-up, return glibc's free pages, cap glibc arenas (without these, host RSS grew by several GB under load). |
| `DS41_ABLATE_CLAMP` | empty (off) | Optional conditional-clamp ablation; see [abliteration.md](abliteration.md). |
| `DS41_MASTER_PORT` | `29961` | Process-group port (the control channel uses this + 31). |
| `DS41_EXTRA_ENV` | — | Extra `NAME=value` settings for every rank, e.g. diagnostics `DS41_STEP_STATS=1 DS41_PREFILL_STATS=1`. |

## 6. Start, use, stop

```bash
engine-rs/serve/start.sh ds41      # on node A; stops whatever model runs first
engine-rs/serve/start.sh status    # ds41
engine-rs/serve/start.sh stop
```

Loading takes about 20 s plus a ~10 s warm-up when the checkpoint pages are cached, longer from a cold disk. Logs:
`/tmp/spark-ds41-rank<r>.log` (on each node), `/tmp/spark-ds41-front.log`. Each request logs one line on rank 0, e.g.
`request: prompt N tokens, prefix M from store|disk|cold`.

The API is the same as for the other models ([deploy.md](deploy.md) §6). DeepSeek-specific behavior of the front end
(`engine-rs/serve/ds41_server.py`):

- **Prompts** are built by the checkpoint's own `encoding/encoding.py` (multi-turn, tools, thinking, mid-conversation
  system messages), so the format follows the official reference exactly. Request conversion follows the official API
  ([deepseek-ai/deepseek-recipe](https://github.com/deepseek-ai/deepseek-recipe)).
- **Control tokens come only from the template.** Special-token text inside a request (content, reasoning, tool
  arguments, results and schemas: `</think>`, `<｜DSML｜…>`, `<｜User｜>`, …) is encoded as ordinary text, and the output
  parser recognizes `</think>` and `｜DSML｜` by token id, so quoted markup can neither open turns or tool blocks in the
  prompt nor turn into tool calls in the reply. Internal message fields (`task`, `wo_eos`, …) are ignored.
- **Sampling**: thinking mode samples at temperature 1.0 whatever the request asks, as the official API does
  (`DS41_THINKING_TEMPERATURE`, empty = use the request's); otherwise `temperature` defaults to 1.0
  (`DS41_DEFAULT_TEMPERATURE`). Without a `seed` each request gets a random one. `top_p`, `top_k` and penalties are
  accepted and ignored. `max_tokens` defaults to 8K without thinking, 64K with thinking and 128K at `max` effort (at most
  the context left).
- **Thinking** is on by default (effort 75). Turn it off with `"thinking": {"type": "disabled"}`,
  `"chat_template_kwargs": {"thinking": false}` (or `enable_thinking`), or `"reasoning_effort": "none"`. Effort levels
  map onto the model's 1–100 budget like the official API: `minimal`/`low` 50, `medium`/`high`/`xhigh` 75,
  `max`/`ultra` 100, or pass an integer; unknown levels are rejected.
- **Tools**: OpenAI `tools` / `tool_calls` / role `tool`; calls are parsed from the model's DSML blocks, output after
  the calls block is dropped. Tool definitions are normalized to `{name, description, parameters}` (`defer_loading`
  tools are not rendered, duplicate names are rejected). `tool_choice`: `none` renders no tools; `required` or a named
  function opens the calls block in the prompt (not in thinking mode, as officially). For prefix-cache hits across
  turns, keep the parts that change per session after the tool definitions, and send earlier assistant turns back
  exactly as received.
- **Structured output / prefix**: `response_format` `json_object` (the prompt must mention "json") or `json_schema` is
  written into the system prompt (a prompt, not constrained decoding); a last assistant message with `"prefix": true`
  is continued.
- **Images**: `image_url` parts (up to 1024 tokens per image); video is rejected with HTTP 400.

## 8. Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| `engine binary differs on rank N` | Install the same binary at `SPARK_BIN` on all three nodes. |
| `no RoCE subnet shared with rankN` | The point-to-point addresses of that pair are not on a common subnet; check `ip -br addr` and cabling. |
| `rank 0 exited`, process-group errors | `SPARK_TP3_IFNAME` missing or wrong on a node, `DS41_MASTER_PORT` in use, or a worker failed: check `/tmp/spark-ds41-rank1.log` / `rank2.log` on nodes B and C. |
| Out of memory / KV pool assertion at start | Another process holds memory on one node, or the previous model is still releasing it: `start.sh stop`, wait, start again. |
| Prefix cache disabled at start | The ranks' identities differ: same binary, checkpoint path, hash file and `DS41_*` settings on all three. |
| Slow cold prefill | Engram rows come from NVMe: use a local NVMe for the checkpoint, not a network or USB disk. |
